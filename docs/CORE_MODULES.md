# Core modules explained

Read this next to the code. Each section says what the module does, how a request flows through it, and which file to open. Paths are relative to the repository root.

## 1. Configuration and start-up

- [apps/api/src/config/app.config.ts](../apps/api/src/config/app.config.ts) lists every environment variable in one Zod schema. If a secret is missing the server refuses to start with a readable message. The same idea as the instructor's `app.config.ts`, but with a safer fail-fast.
- [apps/api/src/main.ts](../apps/api/src/main.ts) creates the app with `rawBody: true` (the webhook needs the exact bytes), calls `configureApp`, and mounts Swagger at `/api/docs`.
- [apps/api/src/app.setup.ts](../apps/api/src/app.setup.ts) holds Helmet, CORS, the global `ValidationPipe` and the exception filter. The tests call the same function, so tests run the real configuration.

## 2. Authentication ([modules/auth](../apps/api/src/modules/auth), [modules/users](../apps/api/src/modules/users))

Flow, matching the instructor's `Auth.docx` notes (DTO and ValidationPipe, controller, service, password check, JWT, response; and JWT strategy on protected routes):

1. `POST /auth/register` or `/auth/login` passes through `RegisterDto` / `LoginDto` (class-validator; email is trimmed and lower-cased).
2. `AuthService.verifyCredentials` loads the user and runs `bcrypt.compare`. Unknown email and wrong password give the **same** 401 text so nobody can discover which emails exist.
3. `buildSession` signs a 15-minute access JWT (`sub`, `email`) and creates a random refresh token. Only the **SHA-256 hash** of the refresh token is stored (`RefreshToken`).
4. `POST /auth/refresh` revokes the used token and issues a new pair, so a stolen old token stops working.
5. On every protected request, the global `JwtGuard` runs Passport's `jwt` strategy ([jwt.strategy.ts](../apps/api/src/modules/auth/jwt.strategy.ts)): signature and expiry are verified, then the user is loaded from the database so deleted accounts are refused. Routes marked `@Public()` skip it.
6. Widget tokens carry `scope: "widget"`. The strategy rejects any token with a scope, so a widget token cannot be used on the dashboard API.

## 3. Per-project permissions ([modules/access](../apps/api/src/modules/access))

This is the heart of the security model: **a user's rights come from their `Membership` row in that project**, not from a global role.

- `ProjectAccessService.requireMember(userId, projectId, roles?)` is the single decision point. Not a member: **404** (hides that the project exists). Member with the wrong role: **403**.
- `ProjectRolesGuard` (global) looks for a `projectId` path parameter. If present, the caller must be a member, and `@ProjectRoles(LEAD, DEVELOPER)` narrows which roles may call the route. It attaches the membership to the request so handlers can read `@CurrentMembership()`.
- Routes keyed by a ticket or build id (`/tickets/:id`, `/builds/:id`) have no `projectId`. Their services load the record, then call `requireMember` with the record's project, so nobody can reach a ticket by guessing its id.
- Data filtering is also done in queries: testers get `where reporterId = me`; clients get builds `where status != DRAFT`.

## 4. Projects and members ([modules/projects](../apps/api/src/modules/projects))

- Creating a project runs in one transaction: project, the creator's `LEAD` membership, an activity record.
- The **widget key** is generated by `generateWidgetKey()` ([common/utils/crypto.ts](../apps/api/src/common/utils/crypto.ts)): a random key with a visible prefix. The database keeps `apiKeyPrefix` (to find the project) and `apiKeyHash` (SHA-256). The full key is returned only on creation and rotation.
- `assertAnotherLead` stops removing or demoting the last Lead. Member operations filter by `projectId`, so a Lead of project A cannot touch a membership id from project B (tested).
- GitHub connection stores `githubRepo` (lower-case, unique) and the webhook secret; `toPublicProject` strips secrets from every response.

## 5. Tickets ([modules/tickets](../apps/api/src/modules/tickets))

- **Workflow table** ([ticket-workflow.ts](../apps/api/src/modules/tickets/ticket-workflow.ts)): `TRANSITIONS[from][to] = allowed roles`. `canTransition` and `allowedTransitions` are pure functions, which is why the permission rules have unit tests. The dashboard shows only the buttons the API would accept.
- **Creating a ticket** (`TicketsService.create`) uses `prisma.$transaction`: increment `Project.nextTicketNo` (a row lock, so two reports cannot get the same number), create the ticket with its events, annotations and artifact, write the activity record. If any step fails, everything is undone.
- **Blocking tickets**: `blockingWhere` (High or Blocker and not Verified) is shared by the build list, the review screen and the approval check, so all three always agree.
- **Visibility**: `loadForUser` returns 404 for a tester asking for someone else's ticket. Technical `events` are not loaded at all for testers.
- Search uses `ILIKE`-style `contains` with `mode: insensitive`; `IF-12` or `12` also matches the ticket number. Sorting is limited to a whitelist.

## 6. Widget ingest ([modules/reports](../apps/api/src/modules/reports))

1. `WidgetGuard` ([widget.guard.ts](../apps/api/src/modules/reports/widget.guard.ts)): checks `X-InspectFlow-Key` against the stored hash (constant-time compare), then requires the browser `Origin` to be in the project's `allowedOrigins` (enforced on the server; CORS alone only affects browsers), then, for `/reports`, verifies the widget token belongs to this project and the user is a member.
2. `POST /widget/login` returns a 2-hour token with `scope: "widget"` and `pid` (project id).
3. `POST /reports` accepts multipart data through `FileInterceptor` (memory storage, 5 MB file limit, size-limited payload field). `ReportsService.submit` validates the JSON payload, validates and re-encodes the image, stores it, then creates the ticket. If the database write fails the stored file is deleted.
4. The Throttler limits requests per client (`WIDGET_RATE_LIMIT_PER_MIN`, login 10 per minute).

## 7. Evidence sanitisation ([common/utils/sanitize.ts](../apps/api/src/common/utils/sanitize.ts))

Applied to every event on the server, even though the widget already cleans them:

- Bearer tokens, JWTs, and `password`, `token`, `api_key`, `cookie`, `session` style key/value text are replaced with `[REDACTED]`.
- URLs lose credentials and the fragment; query values whose key looks sensitive are redacted.
- Methods, status codes and durations are validated and clamped; unknown event types are dropped; at most 200 events; text is truncated.
- The result is stored as plain text and shown by React as text, which is what prevents stored XSS.

## 8. Files ([modules/files](../apps/api/src/modules/files), [providers/storage](../apps/api/src/providers/storage))

- `ImageService.validateAndProcess`: size limit, declared MIME must be PNG, JPEG or WebP, the **magic bytes** must agree, then Sharp decodes and **re-encodes to PNG** (removes metadata and any hidden payload) with a pixel limit.
- `StorageService`: `s3` driver uses the AWS SDK; `local` driver writes under `uploads/`. Object keys are random UUIDs. `signedUrl` returns a 5-minute link: an S3 presigned URL, or for local mode an HMAC over key and expiry that `GET /files/local` verifies. Path traversal is blocked in `localPath`.
- `RetentionService` removes screenshots of tickets verified more than N days ago.

## 9. GitHub webhook ([modules/github](../apps/api/src/modules/github))

`GithubService.handle`:

1. Read `repository.full_name` from the payload, find the project with that `githubRepo`.
2. Compute `sha256=` + HMAC-SHA256(secret, **raw body**) and compare in constant time with `X-Hub-Signature-256`. A wrong or missing signature gives 401 (and an unknown repository gives the same 401). Rejected attempts are recorded.
3. In one transaction: insert the `WebhookDelivery` (its `deliveryId` is unique) then apply the event. A replay fails on the unique insert, the transaction rolls back and the response says `duplicate: true`.
4. Event rules: `ping` answers pong. `pull_request` opened/synchronized links the PR number to tickets whose branch equals the PR's head branch. `closed` with `merged: true` moves linked **Open or In progress** tickets of **that project** to Resolved and logs an automatic activity entry. Closed without merge is ignored.

## 10. Builds and approval ([modules/builds](../apps/api/src/modules/builds))

- Lifecycle: `DRAFT` (developers) to `IN_REVIEW` (shared with clients) to `APPROVED` or `REJECTED`.
- `decide()` runs in a transaction that first executes `SELECT ... FOR UPDATE` on the build row. Concurrent decisions queue up; the second one sees the build is no longer in review and gets 409 (tested with three parallel requests, exactly one wins).
- Approval is refused with 409 while blocking tickets exist. The `BuildApproval` row copies the build's **commit SHA at decision time**, so the record stays true even if the build is edited later.

## 11. Cross-cutting pieces

- [common/filters/all-exceptions.filter.ts](../apps/api/src/common/filters/all-exceptions.filter.ts): one error shape; Prisma `P2002` to 409, `P2025` to 404, `P2003` to 409; unknown errors are logged and returned as a generic 500.
- [common/middleware/request-logger.middleware.ts](../apps/api/src/common/middleware/request-logger.middleware.ts): logs without query strings.
- [modules/activity](../apps/api/src/modules/activity): `ActivityService.log(input, tx?)` can join a transaction, so a log entry commits or rolls back with the change it describes.

## 12. Widget internals ([apps/widget/src](../apps/widget/src))

| File | Role |
| --- | --- |
| `index.ts` | Reads `data-key` and `data-api` from the script tag, creates the API client **before** patching `fetch`, starts the collector, mounts the UI |
| `collector.ts`, `ring-buffer.ts` | Patches `console.error`, `fetch` and `XMLHttpRequest`, listens for `error` and `unhandledrejection`, keeps the last 100 events. Records method, URL, status and duration only. Restores everything on `uninstall()` |
| `sanitize.ts` | Same redaction rules as the server |
| `capture.ts` | `html2canvas` on the visible viewport with the widget itself excluded |
| `editor.ts` | Konva stage for drawing; `export()` rebuilds the image from the original with Canvas 2D |
| `redact.ts` | `pixelate()`: replaces a region with large flat blocks, each the average colour of its pixels. Many-to-one, so not reversible; the exported file never contains the original pixels of that region |
| `ui.ts`, `styles.ts` | Shadow-DOM interface (sign-in, editor, results). All text via `textContent`, so nothing is injected as HTML |
| `api.ts` | Calls the API with the original `fetch` so the widget's own requests do not appear as failures |

## 13. Dashboard ([apps/web/src](../apps/web/src))

- `lib/api.ts`: one `api()` function; adds the Bearer token, retries once after a refresh on 401, and sends the user to `/login` when the session cannot be renewed.
- `lib/auth.tsx`: `AuthProvider` (user, login, register, logout). `app/app/layout.tsx` redirects anonymous visitors.
- `lib/project-context.tsx`: the project layout loads the project once; tabs and buttons depend on `myRole`. The server still enforces everything; the UI only hides what would be refused.
- Filters of the ticket list live in the URL query string, so a filtered view can be shared.
- Validation with Zod on the login, register and profile forms; the server remains the authority.
